# Project status and continuation guide

Last updated: 2026-10-30. This is a development snapshot, not a production-readiness claim. The architecture and project charter describe intended behavior; this document records current implementation and known gaps. Older sections of other documents may lag the code.

## Product boundary

External Ansible, Salt or other collectors retrieve native device data using credentials they control. Product adapters interpret the collected output and translate vendor semantics into Navis's common inventory, routing, policy and NAT models. Navis stores and analyzes normalized data; callers should not have to hand-map vendor policy. Preserve native identifiers, evidence and explicit uncertainty. Never interpret missing evidence as an allow or deny.

## Recommended continuation

The IOS / IOS XE adapter now translates interfaces/VRFs, supported static and explicit-prefix active-RIB routes/ECMP, ordered attached ACL candidates and static host NAT intent through five partial envelopes. Live/Ansible/database validation, CEF/FIB, broader route selection, advanced enforcement and NAT stages remain open. See [IOS.md](IOS.md).

1. Validate NSX VM/vNIC-first DFW exports and exact Applied To behavior. Collect realization, host preparation/exclusions, binding trust and per-NIC/host capacity evidence before completeness promotion. Keep VM-based scope primary and preserve the distinction between packet IP groups and enforcement workloads.
2. Validate Check Point management exports through its scoped policy/NAT adapter. Extend installed/implied/global policy evidence, automatic NAT and gateway packet stages. Keep collection through management; gateway operational queries need an explicit supported read-only mechanism.
3. Validate Palo Alto native pushed/hierarchy, application, NAT and routing outputs through database/graph/trace ingestion. Runtime evidence and unsupported NAT/routing cases remain development work; live validation is not its only remaining gap.
4. ACI is ready for a controlled partial-ingestion pilot. Its effective-policy and routing gaps remain open; pilot readiness does not imply confirmed allow/deny. Validate the vendor adapters against representative data, preserve native identities/enforcement association, and continue common-model and deployment hardening. Callers should not hand-map vendor policy.

## Practical test notes

The user's Windows test environment uses `navis-age-test` and `navis-api-age-test`, with AGE and migrations through 015 applied. Container-mounted source changes and database state are local and may differ elsewhere. Do not commit `navis-test.dump`, credentials, tokens or collected configurations. Adapter source changes require approving the new digest before the existing worker processes normalized submissions.

Run the local Python unit suite from the repository root with `PYTHONPATH=src` and `python -m unittest discover -s tests`. Most recent local run: 238 tests passed (including 18 FortiGate, 21 IOS, 18 Avi and 17 F5 adapter, CLI and evidence tests), including NSX native VM/vNIC membership and attachment, IP-only/mixed Applied To regressions, per-NIC footprint and workload-aware database matching, plus the prior vendor tests and CLI validation. Source-port columns and service JSON details already exist; no new migration is required. The current HTTP trace request does not carry TCP flags, so flag-dependent matches stay unknown. SQL views 014 and 015 were separately checked by the user with rollback-based examples. No live APIC/Palo Alto/Check Point/NSX/Avi/F5/IOS/FortiGate collection or full vendor policy ingestion/trace test has been confirmed. A synthetic FortiGate export was processed through a local Docker deployment (Apache AGE PostgreSQL 16, migrations 001–015) via the API and worker. The common rule matcher now excludes a rule when a present selector definitely mismatches, even if another role is unresolved; previously any rule with a dropped role made every later flow unknown.
