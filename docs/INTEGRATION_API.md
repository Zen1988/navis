## Integration boundaries

An external project can submit normalized inventory/evidence, retrieve a selected graph build, run a connectivity analysis and retrieve recommendation drafts. Vendor collection and translation happen outside the HTTP API. For example, the IOS CLI adapter translates device output into normalized envelopes; Navis receives those envelopes, not device credentials.

The current backend is a prototype with explicit gaps. It is not accurate to treat all remaining work as input normalization alone. Clients must account for separate worker execution, graph preparation, incomplete forwarding/policy semantics and deployment configuration.

| Stage | Current mechanism | What it establishes |
| --- | --- | --- |
| Collect/translate | Collector-side Python adapters and examples | Vendor configuration/evidence translated to common input, with limitations retained |
| Submit | `POST /v1/ingestions` | Authorized raw submission persisted as `pending_identity` |
| Normalize | Operator invokes `navis_api.worker.process_submission` | Identity resolved and supported rows written transactionally, or raw evidence stored |
| Select/build | Operator prepares dataset and invokes `navis_api.graph_builder.build_graph` | A selected collection of snapshots projected into an AGE graph |
| Read graph | `GET /v1/graph-builds/{build_id}/graph` | Device identity projection only; current HTTP connections array is empty |
| Analyze | `POST /v1/traces` | Synchronous candidate analysis plus persisted caller-owned session |
| Retrieve drafts | Recommendations endpoint | Existing draft rows; no firewall deployment or guaranteed background generation |

There is no public HTTP API to register consumers, create identity mappings, approve adapters, run the normalization worker, poll ingestion status, create/list datasets, create/list graph builds, retrieve a stored trace result, delete sessions or deploy recommendations. Agree on an operator/orchestrator handoff for these functions before integrating.

## Connection and authorization

Use a deployment-provided base URL, for example `https://navis.example.net`. Paths below are relative to that origin. Protected endpoints require:

```http
Authorization: Bearer <application-token>
Accept: application/json
```

POST requests also require `Content-Type: application/json`. Send one JSON object per request, not form data, NDJSON or an array of envelopes. UUIDs and timestamps are JSON strings. Send actual JSON integers/booleans/nulls rather than string encodings. Do not depend on incidental Pydantic coercion.

| Endpoint capability | Token scope | Additional database authorization |
| --- | --- | --- |
| Ingestion | `inventory:write` | Active consumer matching token issuer+subject; permission for source namespace |
| Graph read | `graph:read` | Active consumer and permission for every source selected in the build |
| Trace | `analysis:run` | Active consumer and permission for every selected source |
| Recommendations | `analysis:read` | Active consumer and ownership of the unexpired caller session |
| Applications | `application:read` | Endpoint currently always returns 503 after scope authentication |

Possessing a token scope does not grant access to every source or device. Never treat a claimed Navis UUID as an authorization mechanism. A graph with even one selected source outside caller scope is refused as a whole. Recommendation ownership is tied to authenticated consumer, not possession of a session ID.

The default verifier rejects all tokens. For controlled local tests, startup can enable a single static token using `NAVIS_LOCAL_TOKEN` (minimum 32 characters), `NAVIS_LOCAL_SCOPES` (space separated), `NAVIS_LOCAL_ISSUER` (default `navis-local`) and `NAVIS_LOCAL_SUBJECT` (default `local-test`). `NAVIS_DATABASE_URL` enables PostgreSQL processors, graph reader and session storage. The corresponding active consumer/source permissions must already exist. This is a local-test configuration, not an OAuth/OIDC issuance service. No token issuance, refresh or revocation endpoint exists here.

Use HTTPS in deployment. A deployment may additionally require client certificates at ingress; that is an infrastructure agreement, not an implemented certificate-to-consumer API. Device/controller credentials stay with collectors. Request bodies and analysis responses can contain sensitive configuration and addressing; avoid logging tokens or complete payloads by default. Request-size/rate limits and timeout policies are deployment-specific, not advertised API guarantees.

## Endpoint reference

| Method/path | Auth | Success | Purpose |
| --- | --- | --- | --- |
| `GET /health/live` | None | 200 | Process liveness |
| `GET /health/ready` | None | 200 | Configured authentication/ingestion and a limited database/schema query |
| `GET /v1/applications` | `application:read` | None implemented | Currently 503 |
| `POST /v1/ingestions` | `inventory:write` | 202 | Stage one envelope |
| `GET /v1/graph-builds/{build_id}/graph` | `graph:read` | 200 | Device identity projection of a completed build |
| `POST /v1/traces` | `analysis:run` | 200 | Analyze expanded flows and save session |
| `GET /v1/trace-sessions/{caller_session_id}/recommendations` | `analysis:read` | 200 | Retrieve owned, unexpired recommendation drafts |

FastAPI exposes `/openapi.json`, `/docs` and `/redoc` with the default configuration. These documentation endpoints have no scope dependency in this app; an ingress can restrict them. `/` serves the prototype web console and is not a JSON API. There are no pagination parameters, request idempotency keys or bulk ingestion endpoint in the current API. Do not invent `/v1/ingestions/{id}` or `/v1/graph-builds` operations.

### Health

`GET /health/live` returns `{"status":"ok"}`. It does not inspect storage or analysis readiness.

`GET /health/ready` returns `{"status":"ready"}` if a non-default verifier/ingestion processor is configured and a query of `navis.ingestion_submission` succeeds. Otherwise it returns 503 with either `Authentication and database are not configured` or `Database or schema is unavailable` in `detail`. Readiness does not verify every migration, graph availability, source mappings, adapter approvals, session storage correctness or network reachability.

## Ingestion lifecycle

### Request: `POST /v1/ingestions`

```json
{
  "source": {
    "namespace": "collector-site-a",
    "external_device_id": "router-a"
  },
  "adapter": {
    "name": "navis",
    "input_format": "normalized-json",
    "format_version": "1"
  },
  "data_type": "interface",
  "collected_at": "2026-10-30T04:00:00Z",
  "completeness": "partial",
  "payload": {
    "entries": [
      {
        "name": "GigabitEthernet0/0",
        "native_id": "GigabitEthernet0/0",
        "kind": "physical",
        "vrf": "BLUE",
        "addresses": ["192.0.2.1/24"],
        "operational_state": "up",
        "config": {"evidence": "collected"}
      }
    ]
  }
}
```

| Field | Required | Contract |
| --- | --- | --- |
| `source.namespace` | Yes | String length 1–255; registered source namespace with caller permission |
| `source.external_device_id` | Yes | String length 1–255; stable external identity, resolved at collection time |
| `device_mapping` | No | Object containing only optional `navis_device_id` UUID or null |
| `adapter.name`, `input_format`, `format_version` | Yes | Each string length 1–255; current worker supports only the tuple shown above |
| `data_type` | Yes | `device`, `interface`, `route`, `policy`, `nat`, `neighbor`, `mac`, `topology`, `security_zone` |
| `collected_at` | Yes | ISO datetime with timezone, e.g. `Z` or `+08:00`; naive timestamps rejected |
| `completeness` | Yes | `complete`, `partial` or `unknown`; collector evidence assertion, not a connectivity verdict |
| `payload` | Yes | JSON object; normalized types use exactly `{"entries":[...]}` |

Extra fields are forbidden on the envelope and its source/adapter/device-mapping objects. Payload detail validation occurs in the worker, not in the HTTP request model. Therefore an invalid route or selector can receive 202 and later fail normalization. Adapter name/version validity is also enforced later. Omit `device_mapping` unless the operator supplied the correct existing UUID; an unknown claimed UUID can cause an unhandled database FK error rather than a documented 4xx response.

### Response and meaning

```http
HTTP/1.1 202 Accepted
Content-Type: application/json
```

```json
{
  "ingestion_id": "10000000-0000-4000-8000-000000000001",
  "status": "pending_identity"
}
```

`ingestion_id` identifies the staged submission, not a device, snapshot, job completion or graph build. Persist it in your project alongside source identity, data type, collection time and a local payload hash. A successful receipt means the database transaction accepted the envelope. It does not mean normalization was queued or completed. No queue invocation occurs in the endpoint and no `Location`/polling URL is returned.

### Worker outcomes and operator handoff

The trusted worker locks the submission, verifies the supported adapter tuple and approved SHA-256 artifact, resolves exactly one identity valid at `collected_at` (`valid_from <= time < valid_until`, or no end), checks any claimed UUID and validates/writes the payload. It returns a snapshot UUID to its Python caller, not to the original HTTP client.

| Submission state | Meaning | Client action |
| --- | --- | --- |
| `pending_identity` | Accepted/staged; processing still required | Retain receipt; hand off to operator/orchestrator |
| `processed` | Supported typed payload normalized transactionally | Obtain snapshot/build IDs through the agreed operational channel |
| `raw_only` | `device`/`topology` payload preserved without typed normalization | Treat as raw evidence; inclusion/consumption is explicit |

On worker failure, database writes roll back. The current worker does not reliably produce a separate public failed status or an HTTP error record; the operator must report the exception and fix identity/approval/payload issues. Reprocessing an already `processed`/`raw_only` submission raises `submission already processed`.

Each envelope creates a separate snapshot for its one data type. A device's interface, route, policy and NAT envelopes are not one atomic bundle. A vendor CLI often prints an array: split it and POST each element. Group related receipts in your own collection-run record; the API has no collection-run ID field. Combine entries for one device/data type into one intended snapshot where practical. Arbitrary chunking produces separate snapshots, and dataset selection picks one snapshot per device/data type rather than merging chunks.

Use `partial` when unresolved vendor conditions remain. An empty `entries` array is accepted, but `complete` plus an empty collection is an assertion of exhaustive absence, not a way to hide a collection failure. Route completeness alone does not establish installed forwarding. There is no envelope field to populate all coverage details, policy applicability or observed session evidence needed for a definitive analysis.

## Normalized payload reference

For the seven typed kinds below, `payload` must contain only an `entries` array; each entry must be an object. The worker rejects additional entry fields except the optional fields listed. Prefer stable native IDs across snapshots of the same device, and stable VRF/enforcement-point/rule-set identities. Names alone must not conflate devices, tenants, partitions or route domains.

### Interfaces: `data_type=interface`

| Field | Required | Meaning/validation |
| --- | --- | --- |
| `name` | Yes | Nonblank display name |
| `kind` | Yes | Nonblank classification such as `physical`, `virtual` or `unknown`; no closed enum in validator |
| `addresses` | Yes | Array of host interface addresses, e.g. `192.0.2.1/24`, `2001:db8::1/64`; canonicalized with host bits retained |
| `native_id` | No | Nonblank native interface identity; defaults to `name` in worker |
| `parent` | No | Parent native ID in the same envelope; cannot be self or missing |
| `vrf` | No | Nonblank routing-context identity; omitting it leaves context unknown |
| `operational_state` | No | Nonblank state string; not a promise of successful forwarding |
| `vlans` | No | Array of integers 1–4094, retained as details |
| `config` | No | JSON object retaining configuration and uncertainty |

Duplicate native IDs and invalid parent references fail processing. VLAN/config metadata does not automatically establish segment membership or a physical link. A configured VIP interface is configuration evidence, not proof of advertisement/ownership.

### Routes: `data_type=route`

```json
{"entries":[{"vrf":"BLUE","destination":"203.0.113.0/24","next_hop":"192.0.2.254","interface":"GigabitEthernet0/0","route_type":"forward","details":{"evidence":"configured_unverified"}}]}
```

Required keys: `vrf`, `destination`, `next_hop`, `interface`. `vrf` is nonblank; `destination` must be a canonical strict network prefix (use `192.0.2.0/24`, not `192.0.2.5/24`). `next_hop` is an IP or null; `interface` is a stable native ID or null. Optional `route_type` defaults to `forward`; optional `details` is an object.

| `route_type` | Constraints |
| --- | --- |
| `forward` | At least a next hop or interface required; supports recursive next hops |
| `connected` | Interface required; normally send null next hop |
| `discard` | Both interface and next hop must be null |

Destination and next hop must have the same IP version. Route details retain source/native evidence. They are not arbitrary instructions to the routing engine: placing distance/metric/protocol in `details` does not populate the dedicated selection columns. The endpoint does not establish `snapshot_coverage.details.table_kind=installed`; configured routes and active RIB evidence cannot automatically become verified FIB coverage.

### Neighbor and MAC evidence

`neighbor` entries require exactly `interface`, `vrf`, `ip`, `mac`, `state`:

```json
{"entries":[{"interface":"GigabitEthernet0/0","vrf":"BLUE","ip":"192.0.2.254","mac":"00:11:22:33:44:55","state":"reachable"}]}
```

`mac` entries require exactly `interface`, `mac`, `vlan` (integer 1–4094):

```json
{"entries":[{"interface":"GigabitEthernet0/0","mac":"0011.2233.4455","vlan":100}]}
```

MAC input accepts complete colon/hyphen octets, Cisco dotted notation or 12 hexadecimal digits; normalization produces lowercase colon notation. Interface/VRF/state identities must be nonblank. ARP/MAC evidence alone does not establish an end-to-end path. For route/neighbor/MAC/selector records, the worker may create placeholder interfaces within that snapshot; use the same native IDs as the full interface snapshot for reconciliation.

### Security zones: `data_type=security_zone`

```json
{"entries":[{"enforcement_point":"firewall-a:vsys1","zone":"trust","interfaces":["ethernet1/1"]}]}
```

Each entry requires exactly `enforcement_point`, `zone` (nonblank strings) and `interfaces` (array of nonblank native IDs). Match enforcement-point identities with policy/NAT envelopes. Missing or ambiguous interface-to-zone resolution stays unknown. An empty list does not invent zone membership.

### Policies: `data_type=policy`

Required fields: `enforcement_point`, `rule_set`, `default_action`, `rule_id`, `position`, `action`, `enabled`, `selectors`. Optional `details` must be an object. Point/set/rule identities must be nonblank. `position` is a nonnegative integer, `enabled` a boolean, and action/default is `allow`, `deny` or `unknown`.

```json
{
  "entries": [{
    "enforcement_point": "firewall-a:vsys1",
    "rule_set": "security",
    "default_action": "unknown",
    "rule_id": "allow-web",
    "position": 10,
    "action": "allow",
    "enabled": true,
    "selectors": [
      {"role":"source","kind":"address","value":"192.0.2.0/24","negated":false},
      {"role":"destination","kind":"address","value":"198.51.100.5/32","negated":false},
      {"role":"service","kind":"service","value":{"protocol":"tcp","destination_port_start":443,"destination_port_end":443},"negated":false}
    ],
    "details": {"statefulness":"unknown","selectors_complete":false}
  }]
}
```

Rules evaluate in ascending position with first-match intent. Keep positions unique inside a set; clients must not rely on ordering ties. Rules within an enforcement-point/set pair must agree on default action and `details.statefulness` (`stateful`, `stateless`, `unknown`; default unknown). These are worker checks. Statefulness is not observed session support. The worker forces imported `selectors_complete=false` even if the caller sends true. Incomplete conditions must not be promoted to a definitive decision by a client UI.

### Selectors shared by policy and NAT

Every selector has exactly `role`, `kind`, `value`, `negated` (boolean). Empty selector arrays are accepted as unresolved conditions, not match-all. Ordinary matching requires source, destination and service roles; use explicit `any` selectors for intentionally unrestricted roles.

| Kind | Allowed role(s) | Value |
| --- | --- | --- |
| `any` | Any supported role | null; cannot be negated |
| `address` | `source`, `destination` | Host IP or CIDR string; host bits canonicalized for storage |
| `service` | `service` | Service object described below |
| `zone` | `source_zone`, `destination_zone` | Nonblank zone native identity/name |
| `interface` | `interface` | Nonblank native interface identity |

The six supported roles are `source`, `destination`, `service`, `source_zone`, `destination_zone`, `interface`. Repeated positive selectors within one role are OR alternatives; different roles intersect. Negated selectors act as exclusions that must all pass. Unknown conditions remain unknown. Do not flatten correlated source/destination/service tuples into independent OR lists if that creates combinations not present in native policy; retain separate rules or unresolved native evidence.

Service objects require `protocol` (nonblank), `destination_port_start`, `destination_port_end` (integers 0–65535, start <= end). Optional `source_port_start`/`source_port_end` must appear together with the same bounds. TCP-only `tcp_flags_all`/`tcp_flags_any` arrays accept `syn`, `ack`, `rst`, `fin`, `psh`, `urg`, `ece`, `cwr`. All required-all flags and at least one required-any flag must match when arrays are nonempty. HTTP trace input currently has no TCP flags field, so flag-dependent rules stay uncertain. Typed protocol acceptance is wider than the four protocols available in trace requests; schema acceptance does not guarantee protocol-specific semantics.

### Additional policy details

These are structured conditions, not free-form commands:

| Detail | Shape and interpretation |
| --- | --- |
| `application_condition` | Required keys: `applications` (names or null), `any_application`, `application_default`, `complete` (booleans), `default_services` (array of `{application,protocol,start,end}`); optional `incomplete_applications`. Default-service protocols tcp/udp, ports 0–65535. Identity and default services stay paired. |
| `zone_relation` | `universal`, `intrazone`, `interzone`, `unknown`; compares resolved packet zones |
| `interface_condition` | Exactly `{native_id,direction,ip_version}`; direction `in`/`out`, version integer 4/6; requires actual traversal interface |
| `workload_condition` | Exactly `{vif_external_id,direction,ip_protocol,complete}`; direction `IN`/`OUT`/`IN_OUT`/`UNKNOWN`, family `IPV4`/`IPV6`/`IPV4_IPV6`/`UNKNOWN`; requires actual enforcement NIC |
| `inline_rules` | Array of rules with `rule_id`, `action`, `enabled`, `selectors`, optional nested `details`; `inline_default` allow/deny/unknown and boolean `inline_complete`. Child result ends the parent match, including cleanup. Depth is bounded (32). |

Application identity supplied in a trace is a scenario assertion, not runtime App-ID detection. Native ordered-layer intent and vendor details can be retained, but not every vendor pipeline is fully executed by the database trace. See the relevant adapter guide for supported semantics. Extra arbitrary detail keys are preserved; their presence does not make the engine execute them.

### NAT: `data_type=nat`

Required fields: `enforcement_point`, `rule_set`, `processing_stage`, `rule_id`, `position`, `enabled`, `translation_kind`, `translation` (object), `selectors`. Optional `details` is an object. Identities/stage/kind are nonblank; position is nonnegative integer. Rules in one set must agree on processing stage. Selectors use the contract above and remain incomplete after worker import.

```json
{"entries":[{"enforcement_point":"firewall-a:vsys1","rule_set":"nat","processing_stage":"before_route_after_policy","rule_id":"dnat-web","position":10,"enabled":true,"translation_kind":"destination","translation":{"address":"198.51.100.5","port":443},"selectors":[{"role":"source","kind":"any","value":null,"negated":false},{"role":"destination","kind":"address","value":"203.0.113.5/32","negated":false},{"role":"service","kind":"service","value":{"protocol":"tcp","destination_port_start":8443,"destination_port_end":8443},"negated":false}],"details":{"selectors_complete":false}}]}
```

The validator accepts kind/stage strings to preserve unsupported evidence; acceptance does not establish executable NAT semantics. The deterministic common evaluator supports narrow same-family `source`/`destination` address/port translations, `combined` source+destination components, and `no_nat` with an empty translation. Allocation pools, PAT, network/protocol translation and unsupported conditions stay unknown. The database reader also requires a supported processing stage. `before_route_after_policy` and the explicitly implemented `original_addresses_pre_nat_zones_then_post_nat_zone_policy` path have limited handling; the latter retains original policy addresses/ports while resolving NAT and post-NAT zones. Missing routing/zone evidence stays unknown.

`load_balance` at `load_balancer_frontend_backend_connections` represents Avi/F5 frontend/backend candidates; it is not ordinary DNAT. `ios_inside_outside_unverified` and unverified Check Point stages remain evidence, not executed translation. Never strip the stage or convert a backend candidate into a deterministic NAT target to obtain an allow.

### Raw-only types: `device` and `topology`

Their payload can be any JSON object accepted by the envelope. The current worker stores it raw and marks `raw_only`; it does not create typed device records or generic topology links. Device registration is separate. Selected vendor topology kinds include ACI fabric evidence, `avi_load_balancer_evidence`, `f5_load_balancer_evidence` and `ios_device_evidence`. Only explicitly supported readers interpret those structures. Do not invent fields and expect graph projection.

Vendor adapters may emit several envelopes: use their CLI output rather than hand-flattening complex native semantics. Guides: [ACI context/status](STATUS.md), [Palo Alto](PALO_ALTO.md), [Check Point](CHECKPOINT.md), [NSX](NSX.md), [Avi](AVI.md), [F5](F5.md), [IOS](IOS.md).

## Graph response

Call `GET /v1/graph-builds/{build_id}/graph` with a completed build UUID supplied by the operator/orchestrator.

```json
{
  "build_id":"20000000-0000-4000-8000-000000000001",
  "dataset_id":"20000000-0000-4000-8000-000000000002",
  "status":"completed",
  "nodes":[{
    "id":"30000000-0000-4000-8000-000000000001",
    "type":"device",
    "external_identity":{"status":"mapped","namespace":"cmdb-site-a","id":"router-a"}
  }],
  "connections":[],
  "projection_status":"device_identity_only"
}
```

`nodes[].id` is the internal device UUID. `external_identity.id` is the consumer-facing external ID from its configured identity source; it can differ from the collection namespace/ID. Mapping must be valid for every selected snapshot time of that device. Identity status is `mapped`, `missing` or `ambiguous`; the last two contain only status, so do not assume namespace/id exist. Node order is not guaranteed.

`connections=[]` means this HTTP projection does not return edges. It does not establish that devices are disconnected or that the internal AGE graph has no links. `status=completed` describes the build, not connectivity or evidence completeness. Invalid UUID is 422, absent build 404, incomplete build 409, source access denied 403, unconfigured reader 503.

## Trace request

`POST /v1/traces` runs synchronously; it is not a job-submission endpoint.

```json
{
  "graph_build_id":"20000000-0000-4000-8000-000000000001",
  "caller_session_id":"myproject-20261030-7b1c4d",
  "source":"192.0.2.10;192.0.2.11",
  "destination":"198.51.100.5",
  "protocol":"tcp",
  "source_port":51000,
  "destination_port":443
}
```

| Field | Required | Constraints |
| --- | --- | --- |
| `graph_build_id` | Yes | UUID of a completed build in caller scope |
| `caller_session_id` | Yes | String length 1–255, unique per authenticated consumer; prefer URL-safe UUID/ULID-based IDs |
| `source`, `destination` | Yes | Each string length 1–16000 containing literal host IPs separated by commas or semicolons |
| `protocol` | Yes | String length 1–16, normalized to lowercase after trim; tcp/udp/icmp/icmpv6 only |
| `destination_port` | No | Strict JSON integer 0–65535 or null; must be absent/null for ICMP/ICMPv6 |
| `source_port` | No | Strict integer 0–65535 or null; useful for source-port matching/reverse scenarios |
| `application` | No | Nonblank scenario identity, maximum 255 characters; not port-derived App-ID |

Extra top-level fields are forbidden. No hostnames, CIDRs, IP ranges, JSON arrays, VM names, EPG names or zone names are accepted as source/destination. Empty list components and trailing delimiters are rejected. IPs are canonicalized and deduplicated separately on each side; their Cartesian product must be at most 1,000 flows. The example produces two results. Use each result's tuple as its correlation key. The current response does not echo every optional input field, so retain the original request.

No request fields select a tenant/VRF/Applied-To NIC, TCP flags, ICMP type/code, session state or NAT allocation. Endpoint resolution currently matches exact interface host addresses in the selected interface snapshots, not any host contained in an interface subnet. Overlapping addresses across devices/VRFs can be ambiguous; address that in dataset/evidence preparation rather than assuming an IP alone identifies a workload.

A missing TCP/UDP destination port is accepted but can make service matching unknown. Source-port propagation and stateless reverse analysis are partial: supplying `source_port` does not guarantee complete source-port-aware alternative/reverse analysis. Do not infer a verified return path merely because you supplied both ports.

### Success wrapper

```json
{
  "code":"TRACE_RESULT_READY",
  "caller_session_id":"myproject-20261030-7b1c4d",
  "trace_session_id":"40000000-0000-4000-8000-000000000001",
  "graph_build_id":"20000000-0000-4000-8000-000000000001",
  "results":[]
}
```

This illustrates the wrapper only; valid nonempty host input normally produces one result per expanded flow, not an empty list. `TRACE_RESULT_READY` means analysis returned and session storage succeeded. It does not mean traffic is allowed, every flow reached its destination or recommendations are ready. `trace_session_id` is Navis's internal session UUID; recommendation lookup uses `caller_session_id` instead. Store both.

## Interpreting trace responses

Read `results[].connection_verdict` for the aggregate connection assessment. Also retain the candidate-path verdict, coverage, reasons and findings. Do not collapse them into a single undocumented boolean.

### Verdict hierarchy

| Field | Meaning | Consumer interpretation |
| --- | --- | --- |
| `results[].status` | Main candidate-path status (`allowed`, `blocked`, `unknown`) | A blocked candidate does not establish all alternatives are blocked |
| `verdict.status`, `.scope` | Candidate explanation and scope (`candidate_path`, `forward_path`, `end_to_end`) | Display scope with result; do not overstate it |
| `verdict.blocking_point`, `.rule_id`, `.reason` | Blocking device UUID/native rule or null and human explanation | These identify evidence, not deployment instructions |
| `connection_verdict.status` | Aggregate `allowed`, `blocked` or `unknown` | Preferred field for an end-to-end product summary; missing/unrecognized means unknown |
| `connection_verdict.components` | `forwarding`, `nat`, `policy`, `return_path`, each `allow`, `blocked` or `unknown` | Component values deliberately use `allow`, while aggregate uses `allowed` |
| `connection_verdict.missing` | Unestablished requirements | Explain why a result remains unknown; never silently ignore |

An observed candidate denial can yield `status=blocked` and `connection_verdict.status=unknown` simultaneously. That is intentional: another path may remain unresolved. Aggregate blocking requires established complete alternative-path evidence that all paths are blocked/discarded. A reached candidate alone is not an allow. Do not convert `unknown` to allow, deny, false or a successful health check.

For example, these selected fields from an illustrative flow mean “a candidate was denied; the overall connection is unresolved,” not “the whole connection is blocked”:

```json
{
  "status":"blocked",
  "verdict":{
    "status":"blocked","scope":"candidate_path",
    "blocking_point":"30000000-0000-4000-8000-000000000001",
    "rule_id":"deny-web","reason":"matched rule"
  },
  "connection_verdict":{
    "status":"unknown",
    "components":{"forwarding":"unknown","nat":"unknown","policy":"blocked","return_path":"unknown"},
    "missing":["forwarding","nat","return_path","alternative_paths","all_paths_blocked"]
  }
}
```

### Flow-level fields

| Field | Shape/meaning |
| --- | --- |
| `source`, `destination`, `protocol`, `destination_port` | Canonical scenario tuple; optional port may be null |
| `source_candidates`, `destination_candidates` | Arrays of `{device_id,interface_id,interface,vrf}`; zero means unresolved, multiple means ambiguous; VRF can be null |
| `route_candidates` | Source route candidates, not an end-to-end selected path |
| `hops` | Array of evaluated main-candidate hops, possibly empty or stopped early |
| `alternative_paths` | null or bounded search object described below |
| `coverage` | Collection and semantic coverage; collection completeness is not sufficient by itself |
| `findings` | Machine-readable `{code,device_id,message}` entries; device can be null |
| `reasons` | Human explanation strings; do not parse these as stable enums |
| `reverse_trace` | Shape varies with whether reverse analysis ran; not always a second full trace |
| `aci_policy_evidence` | ACI membership/directional-rule candidates, always uncertain in current reader |
| `load_balancer_evidence` | Avi/F5 frontend/backend candidates, not selected sessions |

Route candidate objects contain `route_id`, `prefix`, `route_type`, `protocol`, `preference`, `metric`, `next_hop`, `interface`; many values may be null. The `route_id` is an internal UUID, not necessarily a vendor identifier. UUIDs, names and evidence IDs should not be treated as interchangeable.

### Hop fields

All hops contain `number`, `device_id`, `name`, `platform`, `policy_evidence`, `policy_evaluations`, `packet_before`, `packet_after`, `nat_evidence`. Later-stage fields are conditional because traversal can stop early.

| Conditional field | Interpretation |
| --- | --- |
| `route_assessment` | `status` selected/no_route/unknown, `routes`, `reason`; verified installed table coverage is required for selection |
| `route` | Main candidate route chosen by traversal; its presence alone does not make route_assessment selected |
| `recursive_resolution` | Recursive next-hop chain/status; unresolved recursion stops traversal |
| `resolved_egress_interface` | Native egress resolved through recursion |
| `ingress_interface`, `egress_interface` | Native IDs or null; missing scope matters for ACLs, DFW and zones |
| `translated_destination_candidates` | Endpoint matches after destination translation |
| `stop_reason` | Why this candidate stopped; not a proven whole-network outage |
| `recommendations` | Candidate rule drafts, when generated from deny evidence |
| `policy_coverage` | complete/partial/unknown/conflicting collection state |
| `policy_applicability`, `policy_direction_applicability`, `policy_not_applicable` | Explicit enforcement applicability, not inferred from an empty ACL list |

Packet objects use `{source,destination,protocol,destination_port,source_port}`. Compare `packet_before` and `packet_after` with NAT evidence; do not assume every hop performs translation.

`policy_evidence` is native/configured rule metadata, not proof that every listed rule matched. `policy_evaluations` usually includes enforcement point, rule-set/snapshot IDs, statefulness, session support, `decision` allow/deny/unknown, matched `rule_id` or null, reason and zone context. Some synthesized entries have fewer fields. Unknown session support is distinct from false. `nat_evidence` records status translated/unchanged/unknown, point/snapshot/stage where available, rule ID/reason and stage-related details. Unsupported stages stay unknown even with valid-looking translation addresses.

### Coverage

`coverage.devices[]` contains `{device_id,data_types}` with per-type collection states; missing types mean unestablished coverage. Conflicting selected statements can yield `conflicting`. The flow coverage also includes:

- `destination_reached`: main-candidate traversal reached a target device; not proof of session success.
- `relational_evidence_unchanged`: current selected relational evidence matches the graph build's recorded manifest.
- `forwarding`: `{complete,findings}` assessment of installed forwarding and traversal.
- `forwarding_semantics_verified`: mirrors the forwarding completeness assessment.
- `policy`: `{complete,findings}` including collection and enforcement applicability.
- `return_policy`: per-enforcement stateful/stateless return assessments.
- `return_path_verified`: currently initialized false; do not treat this legacy field as the sole aggregate return decision. Use aggregate coverage/components and reverse evidence.
- `complete`, `missing`: combined forwarding, policy, NAT, return-path, alternative-path and evidence-consistency assessment.

Collection `complete`, semantic `complete`, and an unchanged manifest are different claims. No HTTP request flag bypasses missing coverage. Partial vendor inputs normally produce unknown connectivity even when most configuration is understood.

### Alternative and reverse evidence

`alternative_paths` contains `paths`, `complete`, optional `reason` and `verdict`. Path status can be `candidate`, `blocked`, `discard` or `unknown`, with `hops` as forwarding-state records (`device_id`, `routing_context`, packet fields and ingress). These are a different shape from main trace hops. Searches are bounded (currently 64 hops and 256 paths by default); limit exhaustion remains incomplete. A candidate reached path still requires end-to-end validation. Do not interpret alternative-search completeness as health, runtime session or application success.

`reverse_trace` can be `{status:not_evaluated,reason}` after a blocked candidate, an unknown summary with a reason, a stateless reverse candidate trace, or NAT `nat_session_mappings` plus an optional reverse search under `paths`. NAT mapping entries describe before/after reverse packets and `session_state` observed/unknown; observed tuple evidence still does not prove the whole return route. Reverse work can use a separate database transaction. It is not a packet capture or atomic bidirectional proof.

### Vendor candidate evidence

Both vendor candidate fields contain `{status,candidates,truncated}`. Current status is unknown. `truncated=true` means the bounded response does not enumerate every candidate.

ACI candidates retain snapshot/native rule, observed-unverified group membership, packet direction and uncertain service match. Contract/address membership does not itself prove installed enforcement.

Avi/F5 entries identify `evidence_kind`, snapshot, native virtual-service identity (`virtualservice_uuid` is an Avi UUID or F5 full path), VRF and tenant/partition. They include `frontend`, `listener`, `backend_connection_candidates`, `conditions_complete`, `unresolved`, decision and reason. Backend candidates retain destination/port, pool identity, source-translation intent and unknown source/source-port, health and selection. Even `conditions_complete=true` only describes collected configuration conditions; it is not a successful load-balanced session. TLS/profile metadata does not prove a handshake or application response.

### Finding codes currently emitted

| Code | Meaning |
| --- | --- |
| `SOURCE_UNRESOLVED`, `DESTINATION_UNRESOLVED` | No exact endpoint resolution in selected inventory |
| `SOURCE_AMBIGUOUS`, `DESTINATION_AMBIGUOUS` | Multiple device/interface matches |
| `POLICY_COVERAGE_INCOMPLETE` | Policy collection is missing, partial or conflicting |
| `PATH_EVIDENCE_MISSING` | Candidate traversal stopped for missing/ambiguous path evidence |
| `POLICY_EVIDENCE_INCOMPLETE` | At least one rule-set evaluation unknown |
| `NAT_EVIDENCE_INCOMPLETE` | At least one NAT evaluation unknown |

Preserve unknown future codes and display their message. Messages/reasons are explanatory text and can change without being useful programmatic keys.

## Recommendations and sessions

Call `GET /v1/trace-sessions/{caller_session_id}/recommendations` with the same consumer identity that created the trace and the `analysis:read` scope. URL-encode the caller ID as a path segment; do not substitute the internal `trace_session_id`. Prefer a URL-safe caller ID to avoid slash/path ambiguity.

```json
{
  "code":"RECOMMENDATIONS_UNAVAILABLE",
  "caller_session_id":"myproject-20261030-7b1c4d",
  "trace_session_id":"40000000-0000-4000-8000-000000000001",
  "recommendations":[{"status":"unavailable","result":null}]
}
```

| Code | Meaning |
| --- | --- |
| `RECOMMENDATION_PENDING` | At least one persisted draft row is pending |
| `RECOMMENDATIONS_AVAILABLE` | At least one ready draft and no pending rows |
| `RECOMMENDATIONS_UNAVAILABLE` | No ready or pending rows |

The current save path writes `ready` rows when main hops contain generated drafts, otherwise an `unavailable` row. It does not automatically enqueue a background rule generator. Pending handling exists for persisted rows but does not guarantee progress; polling indefinitely cannot create a recommendation.

A ready row's `result` contains device ID, proposed allow action, source/destination/protocol/destination port, ingress/egress interfaces, source/destination zones and their resolved/ambiguous/unknown status, reason and an inner `status` of `draft` or `incomplete`. Outer `ready` means a draft object exists; it does not mean the inner proposal is complete or approved. Review it against all enforcement and routing evidence. No endpoint deploys it.

Sessions default to 24-hour expiry in the configured store. Missing, expired and another consumer's sessions resolve to 404 in the current owned-session query; an invalid/unregistered consumer can receive 403. No expiry timestamp is returned, so your project cannot calculate exact server expiry solely from the response. Caller IDs are unique per consumer in storage; do not assume expiration frees an ID or cleanup occurs automatically. A duplicate can currently surface as an unhandled database/server error, not an idempotent replay or guaranteed 409.

## Errors, retries and client behavior

Explicit errors normally use `{"detail":"message"}`. Validation errors use FastAPI's structured `detail` array with fields such as `loc`, `msg`, `type`, and sometimes `input`/`ctx`. Do not assume every error body is JSON: an uncaught exception or ingress can return plain text/HTML. Limit captured error text and redact sensitive inputs.

| HTTP | Typical cause | Suggested handling |
| --- | --- | --- |
| 200 | Health, graph, trace or recommendations successful | Inspect semantic codes/statuses; HTTP success is not connectivity success |
| 202 | Ingestion staged | Save receipt, then use agreed operator handoff |
| 401 | Missing/invalid bearer | Obtain valid credentials through deployment mechanism; no refresh API here |
| 403 | Missing token scope or source/dataset/consumer permission | Fix permissions; do not retry unchanged input indefinitely |
| 404 | Missing graph or owned/unexpired recommendation session | Check ID/consumer/expiry |
| 409 | Graph not completed or trace processing raises ValueError (e.g. completed build required) | Resolve state/input; detail text is not a universal retry signal |
| 422 | Request model, UUID, host-list/protocol/flow-limit validation | Correct request; payload worker errors may occur later instead |
| 503 | Disabled/unconfigured service, readiness failure, applications endpoint | Check deployment readiness; bounded retry only when operator expects recovery |
| 500/other 5xx | Unhandled database errors, duplicate sessions, FK constraints, backend/ingress failure | Record sanitized diagnostics; operation outcome may be uncertain |

401 responses from the scope dependency include `WWW-Authenticate: Bearer`. Representative details include `Authentication required`, `Invalid credentials`, `Insufficient scope`, `Source access denied`, `Graph access denied`, `Dataset access denied`, `Session not found or expired`, and service-specific not-configured messages. Do not classify a network failure by matching these human strings.

There is no built-in POST idempotency. Repeating ingestion creates another receipt/snapshot if processed. Repeating trace with the same caller ID is not a safe replay; a trace can have completed but its response been lost. Use a durable local operation record and operator reconciliation for uncertain outcomes. A new caller ID creates a new analysis, not an idempotent retry. GET retries can use bounded exponential backoff with jitter for transport failures/transient 5xx. Respect any ingress `Retry-After` if configured; this app does not promise it. HTTP timeouts do not prove the server rolled back.

The request schema is strict about unknown top-level fields, while response objects have no explicit response models in FastAPI. The OpenAPI snapshot therefore does not fully describe dynamic success bodies; this guide and the implementation supply their interpretation. Consumers should tolerate additional response keys, optional/null evidence and unknown future enum/code values, failing to unknown rather than allow. Pin the deployed commit and compare its `/openapi.json` before adopting a new release; `0.1.0` alone does not encode every evolving contract change.

### Python standard-library client

```python
import json
import os
import uuid
from urllib.error import HTTPError
from urllib.parse import quote
from urllib.request import Request, urlopen

base = os.environ["NAVIS_URL"].rstrip("/")
token = os.environ["NAVIS_TOKEN"]

def call(method, path, body=None):
    data = None if body is None else json.dumps(body).encode("utf-8")
    headers = {"Authorization": "Bearer " + token, "Accept": "application/json"}
    if data is not None:
        headers["Content-Type"] = "application/json"
    request = Request(base + path, data=data, headers=headers, method=method)
    try:
        with urlopen(request, timeout=120) as response:
            return response.status, json.load(response)
    except HTTPError as error:
        # Do not log the token or full input. No automatic POST retry.
        raise RuntimeError(f"Navis returned HTTP {error.code}; reconcile POST outcome") from None

with open("docs/api/examples/ingestion-interface.json", encoding="utf-8") as handle:
    envelope = json.load(handle)
status, receipt = call("POST", "/v1/ingestions", envelope)
assert status == 202 and receipt["status"] == "pending_identity"
# Persist receipt["ingestion_id"] and hand off processing/build preparation.

caller_id = "myproject-" + uuid.uuid4().hex
request = {
    "graph_build_id": os.environ["NAVIS_BUILD_ID"],
    "caller_session_id": caller_id,
    "source": "192.0.2.10", "destination": "198.51.100.5",
    "protocol": "tcp", "source_port": 51000, "destination_port": 443,
}
_, trace = call("POST", "/v1/traces", request)
assert trace["code"] == "TRACE_RESULT_READY"
for flow in trace["results"]:
    verdict = flow.get("connection_verdict", {})
    summary = verdict.get("status", "unknown")
    if summary not in ("allowed", "blocked", "unknown"):
        summary = "unknown"
    print(flow["source"], flow["destination"], summary, verdict.get("missing", []))

_, drafts = call("GET", "/v1/trace-sessions/" + quote(caller_id, safe="") + "/recommendations")
# Inspect both drafts["code"] and each row's outer/inner status; never auto-deploy.
```

For vendor CLI arrays, replace the one-file load with a loop over envelopes and record every receipt independently. If part of a run fails, do not pretend the whole bundle is complete. Neither example implements exactly-once delivery or an orchestration service.

## Operator handoff and verification

Before your project begins calling Navis, obtain:

1. HTTPS origin and deployment authentication requirements; token principal/scopes and source permissions.
2. Registered collection namespaces, stable external device IDs and time-valid identity mappings.
3. Installed schema/AGE dependencies, approved normalized adapter artifact and a trusted worker invocation mechanism.
4. A way to correlate ingestion receipts to processing outcomes/snapshot UUIDs outside the current HTTP API.
5. Explicit dataset selection for all related device/data-type snapshots and topology evidence, then a completed build UUID.
6. Expected evidence limitations and a policy for presenting unknown results without converting them to allow/deny.

Operators can invoke `process_submission(connection_factory, submission_id)` and `build_graph(connection_factory, dataset_id)` from trusted Python automation. These are internal functions requiring a configured database connection factory, not endpoints that another project can call over HTTP. Dataset creation/selection and schema administration remain operational work.

For a controlled integration check: call readiness; submit one known partial interface example; have the operator process/review it; prepare a known build; read its identity projection; run a single-flow trace with a unique caller ID; inspect aggregate verdict/coverage/findings; fetch recommendations under the same principal. Separately test missing token, insufficient scope, invalid IP/extra field, inaccessible build, expired/missing session and uncertain POST outcome handling. A 202 receipt or 200 trace is not an end-to-end test by itself.

The checked-in examples are synthetic documentation inputs. Their UUIDs/source mappings are placeholders and will not work against an arbitrary deployment without replacement. Offline verification uses the repository request models/adapter and mocked HTTP processors; it does not validate live PostgreSQL, AGE or vendor collection.

To reproduce the documentation checks after installing the project and `httpx`, run `python docs/api/verify_contract.py`. Use `--write` to regenerate OpenAPI and request/response fixtures when intentionally updating the contract. The checks cover all eight request examples, three response fixtures, all seven documented API paths, 202 staging and trace/session wrappers, authentication/scope rejection, invalid UUID/IP/extra-field handling, and snapshot drift. They use fake storage and do not start application services. On restricted Windows environments, asyncio's local socketpair may require running this check outside the execution sandbox.
